# Application-only audio assessment

Status: the owner authorized the native integration for a private 0.1.4 test installer. See ADR 020 and the verification record below. The owner subsequently authorized Production publication for manual acceptance. Version 0.1.3 remains the recovery installer.

The installed Electron 45.0.0 declarations and [official display-media API](https://www.electronjs.org/docs/latest/api/session#sessetdisplaymediarequesthandlerhandler-opts) accept Windows system loopback or a WebFrameMain owned by Electron. The latter cannot capture an arbitrary external game process. Selecting a window limits video, not system audio. System loopback may include Blueprint's received call audio.

## Earlier assessment (historical proposal)

- Use a small owned C++ helper around WASAPI process-loopback, without a driver. Microsoft's [application-loopback sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/) documents process-tree inclusion and a minimum Windows build of 20348. Require that capability at runtime; do not promise support on all Windows 10 releases. Windows 11 must still be tested.
- Resolve the selected HWND to its PID in trusted native code with GetWindowThreadProcessId, validate the window remains alive, and include its child processes. Never accept arbitrary renderer-supplied PIDs. Separate launchers/audio services, elevated/protected games and shared browser processes can defeat the expected boundary; reject ambiguous targets or explain the limitation.
- Proposed integration: bounded PCM transport from the helper through narrowly scoped IPC to an AudioWorklet, resampling/backpressure and clock handling, then a MediaStreamAudioDestinationNode track published through LiveKit as ScreenShareAudio. Keep microphone publication independent. Stop the helper and track on stop, room switch, process exit or application exit; never write recordings or substitute system loopback.
- Package a reviewed x64 helper with the installer, built with a pinned Windows SDK/MSVC toolchain. Maintain process validation, crash cleanup, audio timing and OS compatibility separately from Electron updates. Prefer an original implementation against documented APIs; if sample/third-party code is reused, review its exact license and include required notices before adopting it. No dependency or license commitment is made here.
- Acceptance requires two distinct audio-producing applications, receiver-side confirmation that only the selected target is audible, a simultaneous Blueprint call to exclude feedback, independent microphone toggling, and cleanup after target termination. None of those application-only tests has been performed because this capture mode does not exist yet.

## Implemented private test and evidence

- Original WASAPI process-loopback helper, no new native dependency/driver. HWND-to-PID validation includes/excludes process trees, never matches titles. The sandboxed preload adapts the existing getDisplayMedia result, so the existing Production web application and LiveKit ScreenShareAudio/volume controls can be reused without deployment.
- Runtime requires Windows build 20348+ and successful API activation; tested on Windows 11 build 26200. Older Windows unsupported behavior is covered by mocks, not a physical older Windows machine. Multi-process apps may include other windows/tabs or omit separate sibling audio services.
- `node desktop/native/build.mjs --fixture` builds the helper and test-only quiet-tone app. `node desktop/native/verify-isolation.mjs` measured the selected 440 Hz process and its 660 Hz child while an independent 880 Hz process played: about 67 dB rejection of the unrelated tone. Repeated capture, explicit stop and target exit passed. All captured samples stayed in memory.
- `node desktop/verify-capture.mjs` exercised the actual sandboxed picker, native bridge and installed LiveKit SDK against the loopback-only test server. The receiver's ScreenShareAudio contained 440/660 Hz; the unrelated 880 Hz signal was over 70 dB lower, and the Electron renderer's own 990 Hz playback was over 80 dB lower. These are generated Windows audio and receiver measurements, not human audibility or a real Production call. Stopping audio also ended video.
- The same test enumerated 28 real capturable windows (20 owned fixtures), rendered all 28, selected beyond the first page, searched, refreshed and selected the intended HWND. There is no source-count cap in the old or new code. The reported four/five-source condition was not reproduced; the confirmed old limitation was one-time enumeration without refresh. OS exclusions/minimized/protected windows remain possible. Do not describe every open OS window as capturable.
- Browser layout regression uses 24 fixture sources at 780/520 px and emulated 100/125/150% scaling. This does not change or validate physical Windows DPI settings.
- Still manual: real microphone independence, friends in the Production room, games/browser process boundaries, long-run lip sync, target launchers/elevation, physical DPI, actual older Windows, and full NSIS installation/uninstallation. Default remains Sem áudio; application audio is labeled experimental and is never silently replaced by system audio.

Private build: `cd desktop; node build.mjs --production`. Installer/checksum are under `desktop/dist`; the owner subsequently authorized publication without a separate Preview approval. Update `src/lib/windows-release.ts` only after the published assets are verified. Exit the application via the tray before installing. Recovery is to exit and reinstall public 0.1.3, preserving the Production session profile; no server/database migration is involved.
