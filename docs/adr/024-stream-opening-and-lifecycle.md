# ADR 024 — Windows-first opening and provider-observed stream lifecycle

Status: owner-approved implementation and Production release after automated checks.

Keep Discord buttons and announcements as HTTPS fragment invitations. After exchange, Windows browsers on an approved application origin attempt one desktop handoff before acquiring media admission. Only the server's one-use, 60-second ticket enters the registered protocol. A blocked attempt leaves explicit app, browser and verified-download choices; no timer implies installation or silently joins the browser. Windows 0.1.5 already restores its isolated guest window, asks before replacing its transmission, and leaves member calls untouched. No shell changes or installer release are necessary. Capture still requires explicit source selection/confirmation.

Replace the client-driven announcement claim with an environment-isolated Redis publication journal. Authenticated LiveKit webhooks wake reconciliation; their payloads are never accepted as the current media state. Query the guest room and match server guest admissions to actual screen publications. Merge track replacements/reconnects for the same admission within a 20-second absence tolerance. Explicit stops, process closure, disconnects and successful provider revocations all become observed absence. Never report a revoked publisher as ended while provider removal has failed and its screen remains present.

Use the existing authorized Discord webhook with wait=true and retain the returned message ID. On confirmed end, PATCH the start message to remove links/embeds/components, and POST one mention-free end notice. Fenced claims precede POSTs. Duplicate and reordered events cannot issue duplicate posts. PATCH is idempotent and retryable; explicit 429 responses preserve a delayed retry. An ambiguous POST/network/crash cannot be retried safely because Discord incoming webhooks do not provide a documented idempotency key. Record uncertain delivery and do not invent confirmation or blindly repost. Exactly-once external delivery under arbitrary failure is not promised. Old announcements have no stored message IDs and cannot be retroactively edited.

Reconciliation runs inside the signed webhook request (including the grace wait), Next after() for successful guest/owner operations, and the existing daily authenticated cleanup. Webhook failures return 503 for provider retry. This does not depend on an open browser, unload handlers or polling; those provide supplemental wakeups. LiveKit delivery is not guaranteed indefinitely. Provider outages/lost webhooks can delay notices until another event/request/daily cleanup. No queue, paid scheduler, runtime bot token or new service is introduced. Batches are bounded; terminal records are kept for seven days, unresolved message edits for recovery, with a hard journal capacity of 512.

Production requires LiveKit Settings → Webhooks → https://www.blueprint.app.br/api/stream/events, signed with the key matching LIVEKIT_API_KEY. WebhookReceiver validates the signed JWT and exact raw-body digest. Ignore member/unrelated rooms. Bound request size/time; never log authorization, webhook URL, invitations or response bodies. Existing API key/secret and announcement variables suffice.

Tests distinguish real cryptographic signature validation and mocked provider transitions from an actual Cloud webhook, Windows protocol prompt, and friends' audio/video acceptance. Recovery: disable the new LiveKit webhook and revert to the recorded web deployment; keep the publication journal to avoid duplicate recovery notices. No account/chat/data migration or installer rollback is needed.

Sources: [LiveKit webhook authentication/delivery](https://docs.livekit.io/intro/basics/rooms-participants-tracks/webhooks-events/), [Discord execute/edit webhook messages](https://docs.discord.com/developers/resources/webhook).
