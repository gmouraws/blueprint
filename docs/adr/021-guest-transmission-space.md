# ADR 021: Capability invitations for an isolated transmission space

Status: owner-approved implementation and Production release after checks. This extends, not replaces, the authenticated rooms. No account/schema migration or new service is required.

Use one environment-scoped LiveKit room `${LIVEKIT_ROOM_NAME}-guest-stream-v1`, isolated from both member voice rooms and their screen transports. One participant connection publishes and subscribes, with at most eight admissions including pending tokens and unknown active participants. Tokens allow screen video/audio only, no microphone/camera/data/admin. Watch invitations never grant publishing. This cap is separate from the unchanged eight-person member voice cap. A browser session is an admission, not a verified human identity; clearing cookies or using another device is another admission.

The active owner creates 1-hour, 24-hour or 7-day bearer invitations from Meu perfil. The 256-bit random capability is returned once and stored only as a SHA-256 hash in the existing environment-prefixed Redis ledger. It appears only in the URL fragment, not query/path. `/stream` removes the fragment before exchange/media requests and sends no analytics or referrers. The exchange creates a separate random HttpOnly, Secure-on-HTTPS, SameSite=Strict browser cookie scoped to `/api/stream`. The session ends at the earlier of twelve hours or invitation expiry. It is never an account session and cannot authorize member endpoints. No nickname/profile/account prompt or credential persistence in localStorage is used. Neutral labels are explicitly unverified.

Redis locking and fenced saves serialize admission, invitation revocation and token issuance. Media identities are unique per connection, short-lived join tokens are never in links, and rejoining first revokes the previous Cloud identity. Stale tab cleanup is bound to its connection ID. Pending reservations are reclaimed only after the token window plus margin and provider revocation; unknown active occupants count. Service failures fail closed. The bounded ledger retains failed revocations instead of freeing their slots. Bearer access can be shared; the owner UI explains that possession grants access.

Revocation denies new HTTP access immediately and requests LiveKit Cloud token cutoff/removal, including derived Discord viewer invitations. Failures report cleanup pending and retry on subsequent operations, 15-second active-client checks and the existing daily cleanup job. Clients stop media on failed access checks or absolute expiry. As with account media, a short JWT lifetime alone does not disconnect connected peers: server expiry cleanup requires a request or the scheduled cleanup. An idle malicious peer or provider outage can outlast the nominal expiry until that cleanup succeeds. No claim of precise background termination or Cloud revocation testing is made from local mocks. Do not clear the Redis ledger to bypass failed cleanup.

Discord is disabled unless the owner later authorizes/configures both `DISCORD_STREAM_WEBHOOK_URL` and `DISCORD_STREAM_ANNOUNCEMENTS_ENABLED=true`. Only an exact HTTPS discord.com webhook endpoint is accepted; no redirects. An announcement requires provider-observed screen publication and a persisted claim before HTTP send, not opening a picker. Track replacement/reconnect retains that claim. A completed stop clears it. Ambiguous webhook failures are not automatically retried, preferring a missed notice over duplicate posts. The message contains only a neutral label and a derived read-only invitation expiring within one hour/parent expiry, with mentions disabled. No real channel is contacted during this release.

Reuse the existing quality targets, SDK capture, screen viewer, measurements and selected-screen audio control. Subscribe/render screen sources only; `/stream` also has microphone=() Permissions-Policy. Capture requires a button click and native browser source confirmation. Listening is off until explicit playback unlock. Existing authenticated room rendering keeps its fullscreen call controls; the guest viewer omits them.

Keep Windows 0.1.4 and its download unchanged. It has no custom-protocol route and its picker requires an authenticated-call bridge. Adding a capability handoff plus a separate native media mode is not a small safe reuse; this iteration uses the HTTPS browser path. A guest page reached inside the old shell can watch but cannot request its native capture. It explains this limitation and does not advertise application-only audio or an unregistered protocol. Native guest handoff remains a separate follow-up; current authenticated native picker/process audio continue unchanged.

Sources: [LiveKit grants/revocation](https://docs.livekit.io/frontends/reference/tokens-grants/), [Discord incoming webhooks](https://discord.com/developers/docs/resources/webhook#execute-webhook), [allowed mentions](https://discord.com/developers/docs/resources/message#allowed-mentions-object).
