## The question

Can an AI coding agent take a product from specification to production while a human remains in control of the engineering decisions?

Blueprint began as a personal engineering lab. The first project chosen to build was the lab itself: a working system for sharing original Builds, Experiments, and Notes. That made the development process part of the story worth examining.

The question was about boundaries: could the agent have meaningful implementation autonomy while product direction, architecture, security, and publication stayed under human control? This is an account of one build, not a measured experiment or a claim about AI productivity.

## Starting with constraints

Implementation did not begin with code. Repository specifications first established the product purpose, architectural limits, visual direction, content policy, bilingual approach, confidentiality rules, and responsibilities of coding agents. Repository isolation was made explicit as the work progressed.

The repository became a contract between human intent and agent execution. It defined what the agent could implement and what required a human decision. Not every choice was known upfront: the implementation plan and later refinements still needed review.

## Human-directed, AI-assisted

Within the approved scope, the coding agent could implement features, create and modify files, add justified dependencies, refactor, write tests, run quality checks, work with CI, and prepare pull requests.

That autonomy did not transfer decision authority. The product mission, major architectural boundaries, confidentiality and professional-project isolation rules, factual claims about the author, publication, approval, and merge decisions remained human-directed. Visual review also led to concrete refinements before release.

Autonomy works better when the boundaries are explicit. Here, review was part of the development model, rather than a claim that AI independently designed or shipped the product.

## What was built

The delivery path is deliberately small:

**Next.js + MDX → GitHub → CI → Vercel**

Next.js, TypeScript, and Tailwind CSS support a static-first site with repository-owned MDX. English is canonical; reviewed pt-BR translations offer the same content under `/pt`. GitHub Actions runs quality gates, while Vercel Git integration handles deployment.

This trades a publishing interface for changes reviewed in Git and a new build when content changes. The v1 problem did not require a database, CMS, authentication system, or custom backend.

The interesting part is not the stack itself. Repository-level specifications, constraints, tests, and review let a coding agent implement a meaningful portion of the system while preserving human control over what it should become.

## What broke

The first Vercel production deployment failed after Next.js successfully generated the static routes. Blueprint's custom post-build verifier expected `.next/server/app/index.html`. That fixed internal path had worked in the previous local validation context, but was absent in the Vercel build environment.

The issue was investigated, and the verifier was changed to use the prerender manifest and discover rendered artifacts without guessing page filenames. Verification was fixed rather than removed: checks for static routes, indexing, and exclusion of unpublished content remained in place. Regression coverage exercised alternate output layouts, and validation was rerun.

The corrected production deployment succeeded. The custom domain blueprint.app.br was subsequently configured and verified over HTTPS. The first deployment incident is resolved.

The lesson: custom verification should not depend on undocumented or environment-specific framework internals. A check that only works in the environment where it was written can become a deployment failure of its own.

## What I learned

- **Specifications make autonomy useful.** Explicit scope and quality criteria give the agent a concrete contract to work against; they do not eliminate the need to resolve ambiguities.
- **Implementation autonomy and decision authority are different.** Delegating code changes still leaves product direction, review, and publication with the human.
- **Failures belong in the case study.** The deployment failure exposed a fragile assumption and led to a stronger verifier. It is more useful to explain that correction than to present a clean path to production.
- **Simple architecture leaves room to change.** Static content and Git-based review met the v1 need without creating a second system to operate. The trade-off is rebuilding to publish changes.
